# ライブラリとモデルの分割

`fumiori`は共通型・推論・CLI・WASMを管理する。
`fumiori-models`は配布5ファイル・学習・データ準備・評価記録・比較デモを管理する。
`fumiori-data`もモデル側のCargo workspaceへ移した。
推論コードと配布モデルの内容、標準モデルの選択はこの移行では変更していない。

## 互換性と再現

モデル側は`runtime`というGit submoduleで、このリポジトリのコミットを固定する。
`git clone --recurse-submodules https://github.com/ksk001100/fumiori-models.git`で再現できる。
デモ・評価CLI・データ準備の共通型は同じsubmoduleからビルドする。
ライブラリ側のCIは`.github/workflows/ci.yml`の`fumiori-models`の`ref`で結合テストのモデルを固定する。

配布モデルはmanifest・設定・語彙・重み・LICENSEの5ファイルを一組にする。
ロード時は既存の形式・architecture・寸法検証とSHA-256検証を維持する。
`model_version`は配布名のv2/v21やライブラリのバージョンとは別のデータ形式バージョンである。
将来の形式変更ではローダーの互換性検証と回帰テストも更新する。

## 更新手順

1. ライブラリを変更したらRust検証を通す。
2. モデル側の`runtime`を対象コミットへ更新し、モデル側のCargo.lockを必要に応じて更新する。
3. Python・Rust・WASM・実ブラウザーでモデル一覧を検証し、submoduleの更新をコミットする。
4. ライブラリの結合テスト対象を変える場合は、CIのモデルコミットも更新する。

モデル追加時はモデル側のAGENTS.mdに従い、試作も比較デモへ追加する。標準への採用は別の評価ゲートを使う。
両リポジトリを同時に変更する場合も、配布物と評価票のモデル・語彙・生成方針のハッシュの対応を保つ。

## 履歴とローカル成果物

モデル側の`docs/repository-origin.json`に移行元コミットを記録する。
過去の評価票・ハッシュ・出典・モデルファイルはそのまま引き継ぐ。
元リポジトリのGit履歴を書き換えないため、過去のモデルは元の履歴にも残る。
履歴を含む取得容量は、この分割だけでは小さくならない。

既存の`build/`、`target/`、`.venv/`やcheckpointは移動・削除しない。
以前の学習成果をモデル側で再利用する場合は、モデル側の`build/`へ必要な成果物をコピーし、対応する設定とmanifestを照合する。
再学習や標準モデルの切り替えは移行のためには不要。
